## Next

- **GPU tests in CI.** Hosted runners have no GPU, so CI never exercises a kernel. Why: every GPU regression is caught only on the developer machine. Needs a self-hosted runner on an NVIDIA machine, triggered by push or workflow_dispatch only, never by pull requests from forks.
- **Grouped convolutions beyond stride 1.** Grouped strides above 1, odd per-group channel counts and small groups still use the one-thread-per-output kernel. Why: grouped downsampling layers (stride 2) are common in mobilenet-style networks.
- **Fuse batch-norm statistics into the conv GEMM epilogue.** In a profile of `cifar -Dbf16=true -- 1 --gpu --tensor-cores --profile` (re-measured: 14.3 s epoch) the implicit-GEMM convolutions take about 57% of the epoch, the batch-norm column reduction (21868 calls; columnReduceHalf took 58 us per call and 8.5%, and reading two channels per lane as one word brought it to 48 us and 7.2%; four channels per lane gave only 47 us), batch-norm grad input 6.6%, apply 4.1%, the zero arena memset 3.6% and the stem im2col 2.2%. The pack and convert kernels (packHalf, packWeightsRotated, packHalfTransposed, toHalf) add up to 4.3%, so operand packing is not a bottleneck of the training path (the packing cost in bench tc belongs to the non-implicit matmul path). Why: batch-norm statistics and application are over a fifth of the epoch and touch the same feature maps the GEMM already writes.
- **Strict f32 kernel efficiency.** What is left: a weight gradient that reads the output gradient transposed instead of going through transposeF32 (in f32 it cannot use ldmatrix and would need scalar copies into shared memory), and the stem (3 input channels) still builds an im2col matrix. Pairing the B loads into one 8-byte read measured slower and was reverted.
- **Skip the gradient zero-fill.** The zero arena is re-cleared every step (3.4% of a profiled bf16 CIFAR epoch). Design: Var gets a unique id, the tape finds the first writer of each gradient buffer before running backward, and each backward closure stores on the first write and accumulates after. Not started because it breaks the invariant that every backward closure adds into zeroed gradients, touches every op, and max-pool and convolution input gradients write only part of their buffer, so those still need the fill.
- **Batch 128 memory.** If a network ever approaches the scratch arena, bring back a --recompute flag that rebuilds the column matrix in the backward pass instead of keeping it. Why: the im2col paths keep their column matrices for the weight gradient.
- **Transformer heads as one product.** The twelve query, key and value projections of a step run at 0.87 TFLOPS f32 against 3.7 for a fused one, which saves about 175 us of a 9.7 ms step before the permute copies the split needs. Do it when a step is under 5 ms or the permute lands for another reason.
- **CPU convolution scaling.** One thread takes 21.5 s per MNIST CNN epoch and six threads 16.5 s (21.7% scaling efficiency; measured in one session, so not comparable with the README table). At six threads the largest items are batch norm + ReLU (1.11 ms forward, 0.90 backward), the 16->32 weight gradient (0.99 ms) and the 1->16 forward (0.69 ms). The ceiling is the memory-bound elementwise ops and the serial stretches (fc, optimizer, data). A direct loop that skips the column matrix would target the 1->16 convolution, whose column matrix is 25 times the input. `bench cpu` now times im2col and GEMM separately (whole matrix, so im2col is slightly overstated against the chunked library path): 1->16 forward spends 0.259 ms in im2col against 0.080 ms in the GEMM, while 16->32 spends 0.090 ms against 0.191 ms. So only the 1->16 layer was limited by the column matrix, and its forward now runs a direct loop (single channel, no padding, c_out a multiple of the vector width; eight output positions are accumulated together to hide the FMA latency), 0.442 ms to 0.197 ms. Its weight gradient runs the same way (per-thread partial sums added in order), 0.366 ms to 0.199 ms; the 1->16 input is a constant, so there is no input gradient. What is left at six threads is the 16->32 weight gradient (0.98 ms) and batch norm + ReLU.
- **ONNX GPU executor: the remaining host ops.** Slice, Concat, Div, Sqrt and any op outside the list in src/onnx/gpu.zig still bounce through the host (an exported GRU step does at its Slice nodes). Slice and Concat fit the strided elementwise kernel; Div and Sqrt need two small kernels. Why: every bounce is a download, a CPU op and an upload.
- **ONNX GPU executor: memory and layout.** Every activation of a run stays in the scratch arena until the next run, so the batch is limited by --scratch; freeing a tensor after its last user would lift that. Graphs imported from other frameworks have not been tried, only the hand-built NCHW graph in tests/onnx_gpu.zig. cuDNN is not used by the executor.
