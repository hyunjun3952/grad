## Next

- **Grouped convolutions beyond stride 1.** Grouped stride-1 convolutions with a multiple of 16 channels per group run the implicit GEMM per group; grouped strides above 1, odd per-group channel counts and small groups still use the one-thread-per-output kernel. Why: grouped downsampling layers (stride 2) are common in mobilenet-style networks.
- **Fuse batch-norm statistics into the conv GEMM epilogue.** A re-measured profile of `cifar -Dbf16=true -- 1 --gpu --tensor-cores --profile` agrees with the earlier one: the implicit-GEMM convolutions take about 54% of the epoch, the batch-norm column reduction 9.6%, batch-norm grad input 6.3% and apply 3.9%, the zero arena memset 3.4%, the stem im2col 2.1% (one epoch 15.7 s). Why: the batch-norm statistics and application are over a fifth of the epoch and read or write the same feature maps the GEMM already touches.
- **Strict f32 kernel efficiency.** The 128 x 128 two-stage tile is in for the wide shapes; float2 B loads measured slower and were reverted. What is left: a weight gradient that reads the output gradient transposed instead of going through `transposeF32`, which in f32 cannot use `ldmatrix` and would need scalar copies into shared memory; and the stem (3 input channels) still builds an im2col matrix.
- **Batch 128 memory.** The column matrices are kept for the weight gradient, and the strict f32 CIFAR network peaks at 634 MiB of device scratch at batch 128 (569 MiB for the wide model) of the 3072 MiB arena. If a network ever approaches the arena, the first thing to bring back is a `--recompute` flag that rebuilds the column matrix in the backward pass.
- **Skip the gradient zero-fill.** The first writer of a gradient buffer could store instead of accumulate; the zero arena is re-cleared every step (3.5% of a profiled bf16 CIFAR epoch, a 262 MiB memset per step). Design, not started: Var gets a unique id, the tape computes the first writer of each gradient buffer from the node list before running backward (nodes replay in reverse, so the last consumer of a buffer writes it first), and each of the 22 backward closures branches to a store on the first write and to accumulate after. Why not started: it changes the engine's core invariant that every backward closure adds into zeroed gradients, touches the backward pass of every op, and max-pool and convolution input gradients write only part of their buffer, so those buffers still need the zero fill anyway; the correctness risk outweighs the 3.5% while the networks we run fit their arena comfortably.
- **Transformer heads as one product.** Measured first, the way the step graph demands: the twelve query, key and value projections of a step (4 heads x 3, each 2048 x 32 x 128) run at 0.87 TFLOPS f32, a fused 2048 x 384 x 128 projection at 3.7, so the projections drop from about 230 us to about 55 us per step - under 2% of the 9.7 ms step, before the two per-block permute copies the split needs. The heads stay separate until a step is under 5 ms or the permute lands for another reason.
- **bf16 batched matmul in one launch.** Closed without the kernel work: the tape widens a bf16 batched product to f32 (autograd.zig, batchedMatmul), so the per-matrix tensor-core loop in gpu.zig matmul is reachable only as a library entry point (tests/parity.zig checks it) and never from a training step, and the step graph already removed the launch cost the loop would have saved. A batch axis in tileGemm would still make it one launch if a bf16 batched product ever lands on a hot path again.
- **CPU convolution scaling.** Measured in one session on a six-core machine: one thread 21.5 s per MNIST CNN epoch, six threads 16.5 s (21.7% scaling efficiency), and per op at six threads (best of 20): batch norm + ReLU forward 1.11 ms and backward 0.90 ms is the largest item, the conv 16->32 weight gradient backward 0.99 ms (its K is already split so each thread packs only its range of B), the 1->16 image convolution forward 0.69 ms, max pool 0.39/0.28. The scaling ceiling is the memory-bound elementwise ops and the serial stretches (fc, optimizer, data), not the convolutions. A direct loop that skips the column matrix would target the 1->16 convolution, whose column matrix is 25 times the input; split im2col and GEMM timings first.

- **ONNX runtime: NHWC convolutions.** Done: Model.run recognises the exporter's Transpose(0,3,1,2), Conv, Transpose(0,2,3,1) sandwich (single-user wrapped tensors, square windows, group 1) and runs it as one NHWC convolution with the chunked im2col from cpu/ops.zig, so the layout transposes never execute. A batch-wide im2col GEMM measured slower (one large A matrix is bandwidth-bound: 6.5 s for 500 CIFAR images at batch 100 against 4.7 s for the transposes, before the chunked version won at 3.5 s), so the cache-sized chunks stay. The pooling sandwiches still take the transpose path.
- **ONNX import on the GPU.** Imported graphs run on the CPU only. The NHWC sandwich fusion above covers the convolution half; a GPU executor still needs device-side pooling, broadcasting and batch-norm kernels over run-time shapes, or host round trips that would make batch-1 inference slower, not faster. A new subsystem, not started.
- **Multi-GPU on real hardware.** `--replicas` is checked against single-replica training only on one GPU. On several GPUs, test it, then replace the host round trip with device-to-device copies (peer access or NCCL-style), and average batch-norm statistics across replicas.
- **Linux GPU loader.** It compiles but has never run; test it on a Linux machine with a driver.
